# 검수 오케스트레이션 프로토콜

필로가 콘텐츠 검수를 진행할 때 따르는 표준 흐름.
진단평가 7차 검수(95점 수렴)가 웹 배포 후 기본 렌더링 문제(지문 안 보임, 밑줄 안 보임, 지문·문항 겹침)를 하나도 못 잡은 사건(2026-04-23) 이후 재설계된 버전.

---

## 적용 대상

- 진단평가 문항
- 독서수업 콘텐츠 (N단계)
- 글쓰기수업 콘텐츠 (N단계)

## 입력 요구사항 (미충족 시 즉시 반려)

검수 요청을 받으면 아래를 확인한다. **하나라도 빠지면 검수를 시작하지 않는다.**

1. **렌더링된 프리뷰 URL 또는 스크린샷** — 없으면 즉시 반려:
   > "렌더링 결과가 없습니다. 실제 웹 서비스(또는 동일 컴포넌트)에 배포된 상태의 URL/스크린샷을 첨부해주세요. 텍스트/JSON만으로는 검수를 진행하지 않습니다."
2. **콘텐츠 메타데이터**: 트랙(진단/독서/글쓰기), 단계, 문항/레슨 ID 리스트
3. **대상 학년**: 초3 / 초6 / 중1 등 (학생쌤 페르소나 설정용)
4. **배치 크기**: 10~20개 권장. 초과 시 분할 권고:
   > "20개를 초과하면 레지스트리 학습과 검수 품질에 불리합니다. 10~20개 단위로 분할해주세요."

---

## 파이프라인

### Stage 0 — 자동 사전 체크 (LLM 호출 전, 0토큰)

실행 항목:
- `node scripts/validate.js` — 스키마 검증
- 마크다운 문법 유효성 (밑줄/링크/이미지 태그 무결성)
- 렌더링된 DOM 토큰 수 vs 원본 토큰 수 대조 (FR-0002류 검출)
- `review/failure-registry.md`의 `check_method: automated` 항목 전체 실행

**실패 건은 에이전트에 올리지 않는다.** 즉시 작성자(별쌤/책쌤/글쌤)에게 반려.
> 이 단계에서 걸러야 할 건 에이전트 호출까지 안 가는 게 비용·정확성 양면에서 이득.

### Stage 1 — 에이전트 패널 병렬 호출

콘텐츠 유형에 따라 다음 조합으로 **병렬** 호출:

| 유형 | 에이전트 패널 |
|------|-------------|
| 진단평가 문항 | 책쌤 🦉 + 글쌤 🐱 + 편집쌤 ✂️ + 학생쌤 🐿️ |
| 독서수업 | 책쌤 🦉 + 편집쌤 ✂️ + 학생쌤 🐿️ |
| 글쓰기수업 | 글쌤 🐱 + 편집쌤 ✂️ + 학생쌤 🐿️ |

각 에이전트에게 **동일한 입력**을 전달:
- 렌더링된 프리뷰 URL/스크린샷
- 콘텐츠 메타데이터 + 대상 학년
- `review/failure-registry.md`의 Active 항목 전체

**병렬 호출이 원칙.** 순차 호출하면 나노클로의 병렬 처리 레버리지가 무의미해진다.

### Stage 2 — 결과 수합 (합치지 않고 그대로 보존)

각 에이전트 출력을 이슈 단위로 쪼개어 파싱.
**합의 도출 금지. 차이를 그대로 드러낸다.**

이슈 분류 기준:
- **합의된 이슈**: 2명 이상의 에이전트가 지적 (겹치는 항목)
- **갈린 이슈**: 1명만 지적
- **신규 실패 패턴 후보**: 동일 유형 이슈가 배치 내 3회 이상 반복되거나, 기존 레지스트리에 없는 패턴

### Stage 3 — 운영자 리포트 (세 섹션 구조)

운영자에게 제출할 리포트 형식:

```
# 검수 리포트 — [트랙] [단계] 배치 [ID]
생성: YYYY-MM-DD HH:MM
대상 학년: [초3 / 초6 / 중1]
문항 수: N

## 1. 합의된 이슈 (2+ 에이전트 지적 — 수정 필수)
- [item #3] [A-렌더링] 지문 뒷부분이 모바일 뷰포트 밖으로 잘림
  근거: 편집쌤, 학생쌤 공통
  Registry: FR-0001
- ...

## 2. 갈린 이슈 (1명만 지적 — 운영자 판단 대기)
- [item #7] [B-콘텐츠] 선택지 (나) 정답 근거 모호
  근거: 책쌤 지적. 편집쌤/학생쌤은 이슈 없음.
- ...

## 3. 신규 실패 패턴 후보
- 편집쌤이 "문단 간격이 좁아 가독성 저하"를 3회 이상 지적 — Registry 신규 등록 검토
- ...

## 4. Stage 0 자동 체크
- 통과: N건 / 실패: M건 (실패 항목은 이미 작성자에게 반환됨)

## 요약
- 전체 N건 중 FAIL: X / PASS: Y / FAIL_WITH_QUESTIONS: Z
- 핵심 블로커 (1~3줄):
```

### Stage 4 — 운영자 판단

운영자가 이슈 단위로 결정:
- **수용 → 수정 요청**: 작성자에게 반환
- **반려**: 이슈가 아님으로 판단 (기각)
- **레지스트리 등록**: 재발 방지를 위해 Registry Active로 추가

### Stage 5 — Failure Registry 갱신

운영자가 "레지스트리 등록" 표시한 항목 → `review/failure-registry.md` Active 섹션에 추가.
다음 배치부터 Stage 0(자동 체크 가능한 경우)과 Stage 1(에이전트 프롬프트 주입)에 자동 반영.

---

## 금지 사항

1. **렌더링 없이 검수 진행 금지** — 입력 단계에서 거부.
2. **점수 매기기 금지** — 프롬프트/출력/요약 어디에도 "~점" 표현 금지.
3. **에이전트 순차 호출 금지** — 병렬이 원칙. 나노클로 레버리지의 핵심.
4. **에이전트 의견 합치기 금지** — 수렴 강제하면 적대적 에이전트 가치가 사라진다.
5. **배치 50개 이상 단일 처리 금지** — 레지스트리 학습 시간이 없다.
6. **검수 차수 누적 자랑 금지** — "7차 검수 완료" 같은 표현은 품질 신호가 아니다. 검수 차수가 많다는 것은 파이프라인이 약하다는 신호.

---

## 출력에 절대 포함하지 말 것

- 종합 점수 ("이 배치는 88점입니다")
- 에이전트 간 합의 도출 문구 ("책쌤은 A라 했지만 종합적으로 B로 판단")
- "대체로 양호함" / "약간 개선 여지" 등 모호 표현

## 트러블슈팅

**"적대적 에이전트(편집쌤/학생쌤)가 아무 이슈도 안 찾음"**
→ 프롬프트가 약한 신호. 실제 렌더링 결과가 제대로 전달됐는지 먼저 확인.
렌더링이 멀쩡했다면 프롬프트의 체크 항목(A–E)을 더 구체화.

**"3 에이전트 모두 전혀 다른 이슈를 지적 (합의 0)"**
→ 정상. 운영자에게 그대로 올린다. 이게 적대적 설계의 목적.
운영자가 "이건 편집쌤 기준 과도함", "저건 학생쌤 관점 수용" 식으로 개별 판단.

**"레지스트리가 계속 커져서 프롬프트가 길어짐"**
→ 3개월 이상 재발 없는 항목은 Resolved 섹션으로 이동(삭제 금지).
프롬프트 주입 시 Active 항목만 포함.

**"작성자가 '렌더링 필요 없이 먼저 텍스트 검수만 받고 싶다'고 요청함"**
→ 거부. 오늘(2026-04-23)의 사건이 바로 이 예외 허용에서 발생했다.
렌더링 프리뷰 없이는 검수 시작 금지.
